# CI 验证、镜像发布与安全检查

发布流程只依赖后端测试、镜像构建和启动冒烟。安全检查独立提供维护报告，不要求镜像或依赖的漏洞数量清零。

## 触发条件

| 工作流 | 自动触发 | 手动触发 |
| --- | --- | --- |
| Backend Tests | 修改后端构建上下文或该工作流的 PR | 由镜像发布流程通过 `workflow_call` 调用 |
| Frontend Build | 修改前端构建上下文或该工作流的 PR | 无独立手动入口 |
| Build Docker Images | main 上两端构建上下文、两端验证工作流、发布工作流或冒烟脚本变更 | 支持选择 Git ref 发布 |
| Security Checks | 每周一 UTC 02:00，即新加坡时间 10:00 | 支持手动检查，无额外输入参数 |

构建与发布使用正向路径过滤，排除 Markdown 和两端 `docs/` 目录；仅修改根目录文档、`docs/screenshots/` 截图或独立安全检查配置不会触发发布。修改源码、依赖锁文件、Dockerfile、`.dockerignore` 等构建输入仍会触发对应流程。混合修改源码和文档时按源码变更执行。

main 的后端测试只由镜像发布流程调用一次，后端工作流不再单独监听 push。PR 测试与合并后测试各执行一次，用于验证合并前代码和实际发布提交。

## 验证与发布过程

1. 后端使用既有 Java 17 补丁版本执行 `./mvnw -B -ntp verify`，保留 Maven 缓存和测试报告。
2. 测试通过后，两端镜像各构建一次，加载到发布 job 的本地 Docker。前端安装与编译由 Dockerfile 完成，发布流程不再额外执行一次 npm 构建。
3. 执行既有隔离网络冒烟，检查页面、同源反代、部分参数校验和匿名认证边界，并检查运行身份。失败时输出容器日志。
4. 冒烟通过后登录 GHCR，将这批本地镜像推送为 `sha-<完整提交号>` 和 `prod`，记录两端镜像摘要。

后端测试、任一镜像构建或冒烟失败都会停止后续推送。后端测试工作流不再额外构建一次 Docker 镜像；`verify` 的测试打包与 Docker 内打包各自保留，不跨 job 传递 JAR。

在 GitHub 仓库的 Actions 页面选择 **Build Docker Images → Run workflow** 可手动发布，使用所选 ref 的代码。现有并发设置保持不变，新运行可以取消同一 ref 下正在进行的发布。

镜像推送仍逐个进行，两端 `prod` 更新不是原子操作；网络失败或取消可能只完成部分推送。生产需要明确版本时，应使用摘要或提交标签，不仅依赖 `prod`。

## 独立安全检查

**Security Checks** 没有 push 触发，也不在发布流程的 `needs` 链中。定时和手动运行均检出仓库默认分支；手动选择其他 ref 不会改变实际被审计的源码分支。

- 两个独立矩阵任务拉取当前 GHCR `prod` 镜像，记录实际摘要后按该不可变摘要扫描。单个镜像检查失败不会取消另一个任务。
- npm 任务记录默认分支实际检出的提交号，直接对锁文件执行官方 registry 审计，不安装依赖、不运行生命周期脚本或前端构建。
- Trivy 沿用 v0.70.0，报告包含所有严重等级和未修复项，不再使用漏洞忽略文件；不导出 SBOM。
- 有漏洞时任务输出 warning，并在运行摘要突出 HIGH/CRITICAL 数量，任务仍成功。npm 数量按受影响依赖条目统计，Trivy 数量按扫描发现条目统计，不代表去重后的 CVE 数量。
- 镜像拉取、数据库下载、registry 访问或报告解析失败会让相应安全任务失败。npm 的退出码 1 只有在报告结构、计数和漏洞条目相符时才作为漏洞结果接受，不能直接忽略所有非零退出码。

在 Actions 页面选择 **Security Checks → Run workflow** 可立即检查。各任务只使用源码读取权限，镜像任务额外使用 packages 读取权限。该工作流不创建 Issue 或发送外部消息；GitHub 自身的 Actions 通知由个人设置决定。

安全结果用于判断维护优先级：结合是否启用相关功能、调用路径、外部输入和当前部署条件评估。已确认可利用的高影响漏洞应暂停发布并修复；无法确认利用条件的告警应继续调查，不能直接当作不存在。发布成功与扫描无告警均不代表系统没有漏洞。

## 报告位置与验证

在对应 Actions 运行的 Artifacts 区域下载报告：

| Artifact | 内容 | 保留时间 |
| --- | --- | --- |
| `backend-validation` | 后端 Surefire XML 测试报告 | 仓库默认设置 |
| `image-release-info` | `release-reports/` 中的提交号、已完成发布的镜像摘要 | 仓库默认设置 |
| `security-backend`、`security-frontend` | 镜像标签、实际摘要和原始 Trivy JSON | 30 天 |
| `security-npm` | 实际提交号、原始 npm JSON 和审计退出码 | 30 天 |

发布与安全任务均使用 `if: always()` 尝试上传已生成的报告。执行过早失败可能只有来源信息或不完整 JSON，应结合失败日志查看，不表示检查通过。安全检查审计的是运行时的默认分支和已发布镜像，两者不保证来自同一个提交，应按报告中的提交号和镜像摘要分别追溯。

本地可在仓库根目录运行以下检查，无需生产凭据：

```bash
# 工作流语法与内联 shell 检查；安装 shellcheck 后 actionlint 会一并调用。
actionlint
bash -n .github/scripts/smoke-images.sh

# 覆盖各等级漏洞、registry/数据库错误报告、损坏 JSON 与退出码不一致等边界。
python .github/scripts/test_security_reports.py -v
```

修改流程后的首次 main 发布仍需在 GitHub 验收实际构建、冒烟、GHCR 标签和报告摘要；本地检查不推送镜像。现有冒烟不依赖真实数据库，不能替代数据库业务集成测试或生产部署验收。本次未修改业务代码、依赖版本、Dockerfile 或部署配置。
